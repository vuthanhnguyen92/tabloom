# Tabloom Cross-Browser Local OAuth Design

## Objective

Make the existing Tabloom extension installable and functional from local packages in Chrome, Arc, Dia, Firefox, and Safari on macOS. All browser packages must preserve the same organizer UI, local-first behavior, Supabase workspace synchronization, bookmarks, tab capture, duplicate handling, spaces, collections, ordering, and theme behavior.

This work does not publish or submit Tabloom to the Chrome Web Store, Mozilla Add-ons, or the Mac App Store. Safari on iPhone and iPad remains outside scope.

## Constraints

- Chrome, Arc, and Dia share one Chromium package and one stable development extension ID.
- Firefox uses a separate stable Gecko add-on ID and a developer installation.
- Safari uses an Xcode-generated macOS Safari Web Extension wrapper signed with **Sign to Run Locally**.
- Local workspaces remain fully usable when Supabase is absent, authentication is cancelled, or the network is unavailable.
- Supabase remains authoritative only after the user signs in and confirms any required non-empty local/cloud merge.
- The Google OAuth client keeps only the Supabase provider callback. Browser-family callbacks are configured in the Supabase Auth redirect allowlist.
- No service-role key, OAuth client secret, authenticated browser session, Apple signing material, or Chromium private key is committed.

## Selected Architecture

The shared application continues to depend on a typed `BrowserAdapter`. Browser-specific authentication implementations normalize their results into the same callback contract, leaving Supabase session exchange and organizer state management in shared TypeScript.

```text
Shared organizer UI, repositories, and PKCE session exchange
                          |
                    BrowserAdapter
              /-----------+-----------\
        Chromium        Firefox       Safari
      identity API    identity API   native message
          |               |              |
          +---------- Supabase OAuth ----+
```

The normalized authentication boundary returns one of four outcomes:

- a callback URL containing an authorization code;
- user cancellation;
- a timeout;
- a provider or platform error with a safe, actionable message.

The shared authentication coordinator parses the callback, rejects mismatched callback origins or schemes, exchanges the PKCE code through `supabase.auth.exchangeCodeForSession`, and returns the resulting session. It never stores credentials in a URL, log, manifest, or repository file.

## Chromium: Chrome, Arc, and Dia

Chrome, Arc, and Dia use `extension/manifests/chromium.json` and the existing Chromium adapter.

A one-time local script generates an RSA key pair. The private key is written to a gitignored local key directory and is not included in any distribution. The public key is encoded as the manifest `key` value and committed. Chrome derives a stable extension ID from that public value, so the unpacked extension has the same identity when loaded from `dist-extension/chromium` in Chrome, Arc, or Dia.

The adapter continues to use:

```text
chrome.identity.getRedirectURL("auth-callback")
chrome.identity.launchWebAuthFlow(...)
```

The build writes a machine-readable callback report containing the stable extension ID and:

```text
https://<stable-extension-id>.chromiumapp.org/auth-callback
```

The report contains no token or secret. The exact callback is added to Supabase Auth URL Configuration.

## Firefox

Firefox uses `extension/manifests/firefox.json`, the existing WebExtension adapter, and the explicit Gecko ID:

```text
tabloom@tabloom.app
```

The explicit ID prevents Firefox from assigning a different temporary identity after each developer installation. The build produces a Firefox package for `about:debugging` and supports `web-ext run` for repeatable local smoke testing.

The package obtains its callback with:

```text
browser.identity.getRedirectURL("auth-callback")
```

A development-only callback reporter exposes the exact value through the build verification command. The exact returned URL, rather than a guessed Firefox domain, is added to Supabase Auth URL Configuration.

The package remains a developer installation. Persistent public distribution would require Mozilla signing, which is outside this design.

## Safari on macOS

Safari uses the shared Safari Web Extension output plus a retained Xcode wrapper generated by `safari-web-extension-converter`. The wrapper uses stable local bundle identifiers:

```text
app.tabloom.mac
app.tabloom.mac.extension
```

The Safari manifest receives `nativeMessaging`. Shared TypeScript calls `browser.runtime.sendNativeMessage` with the Supabase authorization URL and expected callback scheme. `SafariWebExtensionHandler` validates that the request is a Tabloom authentication request, starts `ASWebAuthenticationSession`, and accepts only:

```text
tabloom://auth-callback
```

The Swift bridge returns the callback URL or a normalized cancellation/error response to TypeScript. The PKCE verifier stays in the Supabase JavaScript client's extension storage. Swift never receives, stores, or exchanges the verifier, access token, or refresh token. Shared TypeScript extracts the authorization code and performs the existing PKCE exchange.

The Xcode wrapper is built with **Sign to Run Locally** and Team set to None. Local setup requires Xcode, Safari's Develop menu, and **Allow Unsigned Extensions**. Apple Developer Program membership is not required for this local test package.

Generated callback values are copied from build reports and committed documentation, not inferred during runtime setup.


The Supabase project URL and anonymous key remain public build inputs. The Google client secret remains configured only inside Supabase.

## Local Data and Synchronization

Authentication is optional. Every package starts from its own browser-local `storage.local` workspace when no valid Supabase session exists. Failed or cancelled authentication does not clear, replace, or lock local data.

After successful sign-in, the existing first-sync behavior remains unchanged:

- an empty local workspace imports cloud state without confirmation;
- an empty cloud workspace uploads local state without confirmation;
- two non-empty sides show the existing merge confirmation;
- stable record IDs drive comparison;
- duplicate saved links in the same workspace and collection are deduplicated according to the existing merge rules;
- canonical cloud order is fetched after synchronization.

Each browser has its own local cache. Supabase is the cross-browser synchronization channel.

## Error Handling

All browser adapters map platform errors into shared categories:

- `cancelled`: the user closed or rejected authentication;
- `timeout`: no callback arrived within five minutes;
- `redirect_not_allowed`: Supabase used the site URL instead of the expected browser callback or the returned callback does not match;
- `provider_error`: Supabase or Google returned an OAuth error;
- `platform_unavailable`: the browser identity API or Safari native bridge is unavailable;
- `invalid_callback`: the callback has the wrong origin, scheme, state, or lacks an authorization code.

The extension displays retryable, browser-specific guidance. Redirect failures include the expected callback URL so the developer can update Supabase. Messages never include query values, fragments, codes, or tokens.

An expired Supabase session disables cloud synchronization, preserves local data, and offers sign-in again. Offline writes remain queued or retryable under the existing local-first repository behavior.

## Build and Packaging

The extension build script remains the single entry point and gains browser-specific validation and packaging output:

```text
dist-extension/
  chromium/
  firefox/
  safari/
  reports/
    chromium-auth.json
    firefox-auth.json
```

The Safari converter produces a retained project under `extension/safari/Tabloom`. Generated Xcode files are committed so subsequent builds do not depend on regenerating identifiers or manually reapplying Swift changes.

Build commands produce:

- a Chromium unpacked directory for Chrome, Arc, and Dia;
- a Firefox development ZIP/XPI plus a `web-ext run` command;
- a Safari Web Extension directory and Xcode macOS app project;
- callback reports and an installation guide for every target.

## Testing

### Unit tests

- callback URL validation for Chromium, Firefox, and Safari;
- authorization code and OAuth error parsing;
- cancellation, timeout, and missing-platform normalization;
- callback reports contain only public identifiers and URLs;
- local data remains unchanged after every authentication failure;
- the shared PKCE exchange runs only after a validated callback.

### Manifest and build tests

- Chromium manifest includes a valid public `key` and derives a deterministic ID;
- Firefox manifest retains `tabloom@tabloom.app`;
- Safari manifest includes `nativeMessaging` and excludes unsupported permissions;
- all packages contain the same shared organizer entry point and required assets;
- production builds contain Supabase public configuration but no forbidden secrets;
- each package passes its browser-specific manifest validation.

### Browser smoke tests

- Chrome, Arc, and Dia load the same Chromium directory and report the same extension ID;
- each Chromium browser replaces the new-tab page, persists local data, signs in, and synchronizes;
- Firefox replaces the new-tab page, retains its developer ID, signs in, and synchronizes;
- Safari builds successfully in Xcode, replaces the new-tab page, completes native OAuth, and synchronizes;
- cancellation and a deliberately unregistered callback leave the original local workspace intact in every target.

### Cross-browser acceptance

Sign in to two browser packages with the same Google account. Save a link in the first browser, synchronize, then synchronize the second browser. The second browser must show the same stable space, collection, link IDs, and ordering. Reordering in the second browser must appear in the first after its next synchronization.

## Delivery

Delivery consists of source changes, automated tests, three local package outputs, the Safari Xcode wrapper, callback reports, and an installation/configuration guide. Store submissions, store assets, public signing, and Safari mobile support are excluded.
